# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Текущее состояние

Что запущено, что уже сделано и как продолжить работу в новом сеансе — в `STATE.md`. Список задач — в `tasks.md`.

Путеводитель по папке для людей — `README.md` (что где лежит, ссылки на главные документы). При появлении новых документов и папок дополнять его и проверять ссылки: `python -I -X utf8 tools/readme_links_check.py`. Имён людей, учётных записей и названий исключённых заведений в нём быть не должно.

В каждой папке лежит свой `README.md` с описанием и ссылками на файлы и подпапки (просьба пользователя от 16.11.2026). Их создаёт и обновляет `python -I -X utf8 tools/dir_readmes.py`; тексты описаний — в `tools/dir_readmes.json` (для новой папки добавить туда запись), перечень файлов программа составляет сама. В хранилища сырых копий и медиа (`raw/`, `screenshots/`, `media/` и глубже, `frames/`, `sheets/`, `pages/`) описания не кладутся: там доказательства, и перечни `manifest.jsonl` должны сходиться с диском. Написанные руками `authorities/README.md` и `sources/onsite/README.md` программа не переписывает, а ведёт в них только блок «Что в этой папке». Все ссылки разом проверяет `python -I -X utf8 tools/readme_links_check.py --all`.

## Журнал изменений и коммиты

Требование пользователя от 16.11.2026: «на каждое изменение тепреь надо делать комит. и самое галвное записывать в ридми файл изменения и чеджлог». Порядок для каждого изменения (одна решённая задача — одно изменение, а не каждое сохранение файла):

1. Сделать изменение и, если появились новые документы или папки, отразить их в `README.md` и обновить описания папок: `python -I -X utf8 tools/dir_readmes.py`.
2. Добавить запись в журнал: `python -I -X utf8 tools/changelog.py add "<что изменилось и в каких файлах>"`. Команда пишет запись в `CHANGELOG.md` и обновляет блок «Последние изменения» в `README.md`. Запись — одно-два предложения простыми словами, без имён людей, учётных записей и названий исключённых заведений.
3. Проверить ссылки: `python -I -X utf8 tools/readme_links_check.py --all`.
4. Сделать коммит со всеми файлами изменения: `git add -A`, затем `git commit` с коротким заголовком по-русски. На коммиты разрешение постоянное, спрашивать не нужно.
5. Сразу после коммита отправить его в GitHub: `bash tools/git_push.sh`. На это разрешение тоже постоянное: решение пользователя от 16.11.2026 — «Да, сразу».

Запись в `tasks.md` и обновление `STATE.md` это правило не отменяет: журнал — короткая лента для людей, подробности остаются там.

## Суть проекта

Это не программный проект, а юридико-аналитическая работа. Мы собираем и систематизируем сведения о нарушениях, которые допустило юридическое лицо, работающее как ресторан «Амазонка» в г. Могилёве (Республика Беларусь). От действий ресторана и его владельцев пострадали пользователь и его друзья. Конечная цель — правильно оформленные обращения в компетентные государственные органы.

Работа идёт по этапам, каждый опирается на результат предыдущего:

1. **Карточка юрлица** — точное наименование, УНП, юридический и фактический адреса, руководитель. Источник — ЕГР (egr.gov.by) и другие официальные реестры, а не соцсети.
2. **Сбор материалов** — рассказы пострадавших, документы (чеки, договоры, переписка, фото и видео), публичные публикации в соцсетях и на площадках отзывов: в первую очередь Threads и Instagram, а также TikTok, VK, Одноклассники, Facebook, Telegram-каналы и чаты, отзывы на Яндекс Картах, Google Maps, relax.by, TripAdvisor и т. п. Нужны аккаунты самого заведения и его владельцев (в части, касающейся заведения), отзывы и комментарии.
3. **База эпизодов** — текстовая база: одна запись на каждый отдельный эпизод нарушения (формат ниже).
4. **Правовая квалификация** — для каждого эпизода подбираются нормы права РБ по всем отраслям: налоговой, административной, трудовой, санитарно-эпидемиологической, архитектурно-строительной, по защите прав потребителей, пожарной безопасности, гражданско-правовой и при наличии оснований уголовной.
5. **Реестр органов** — какой орган компетентен по какой норме и по какому эпизоду, с точными реквизитами для Могилёва и Могилёвской области.
6. **Обращения** — отдельное письмо на каждый орган и повод, сгруппированное по компетенции.

## Структура папок (создавать по мере работы)

- `entity/` — карточка юрлица и связанных лиц, выписки из реестров.
- `sources/` — сырые материалы без правок: скриншоты, сохранённые посты, письменные рассказы пострадавших. Имя файла: `ГГГГ-ММ-ДД_источник_краткое-описание`. Для соцсетей обязательно указывать URL и дату фиксации.
- `db/episodes/` — по одному файлу на эпизод: `NNN-краткое-название.md`.
- `db/index.md` — сводная таблица эпизодов: №, дата, суть, отрасль права, статус доказанности, органы.
- `law/` — выписки норм с полной цитатой, реквизитами акта, редакцией и датой проверки.
- `authorities/` — реестр органов: наименование, адрес, способ подачи (почта, приём, электронное обращение), компетенция, какие эпизоды к нему относятся. Начат 15.11.2026: сводка и статус сверки — `authorities/README.md`; сырые копии страниц органов — `sources/official/2026-11-15_authorities/` и `sources/official/2026-11-15_mogilev-gov/`.
- `letters/` — проекты обращений: `<орган>_<повод>.md`, итоговые файлы при необходимости в .docx. Приложение с перечнем публикаций собирает `python -I -X utf8 tools/letter_appendix.py letters/_src/<имя>.json letters/<имя>.md`: выдержки проверяются по `sources/reviews/ALL.jsonl`, имена авторов не выводятся. В конце каждого проекта — справка «откуда каждый факт».
  - **Действующий набор — девять писем от 16.11.2026** (П1–П9: санитарная служба, горисполком, природоохранный орган, налоговая инспекция — по обоим заведениям); перечень — в корневом `README.md`. Каждое письмо принято двумя независимыми оценщиками с оценкой не ниже 9,5 по каждому из восьми критериев.
  - **Стандарт письма — `letters/STANDART.md`** (структура, обязательные формулировки, 67 требований раздела 8, критерии К1–К8). Новое письмо и любая правка — только по нему; форму проверяет `python -I -X utf8 tools/letter_standard_check.py letters/<имя>.md`.
  - **Проверка писем — `letters/_review/<дата>/`:** замечания оппонента и верификатора, ответы составителя (`otvety/`), итоговые оценки (`ocenka/`, задание оценщику — `ZADANIE_ocenka.md`); сводка — `python -I -X utf8 tools/review_summary.py letters/_review/<дата> --write`. После любой правки принятого письма — подтверждение оценщиком. С 17.11.2026 есть третья роль — независимый оценщик «с чистого листа» (роль В в `ZADANIE_ocenka.md`; файлы `…__c.json`, круги `__c2`, `__c3`): он не видит прежних кругов, проверяет нормы сплошь и пробует письмо «отпиской» — отказом со ссылкой на тайну и уходом по сроку. Письмо считается принятым, когда у всех трёх оценщиков в последнем круге не ниже 9,5 по каждому критерию. С 17.11.2026 после правки нескольких писем проводится **сводная проверка набора**: отдельный исполнитель читает все письма подряд и ищет расхождения между ними (один факт, норма, сокращение акта, реквизит и указание шапки — одинаково во всех письмах; правило стандарта, применённое в одном письме, — во всех, где тот же случай). Результат — `ocenka/_svodnaya-proverka_<дата>.json`, ответы — записи `svodnaya:С…` в `otvety/`. Формулировки, общие для нескольких писем, задаются одним заданием и вносятся дословно (образец — `letters/_review/2026-11-16/dop_2026-11-17/ZADANIE_svodnye-pravki.md`); объём писем на пределе, поэтому каждую вставку возмещают сокращением повторов и показывают сокращения оценщику. После правок, сделанных после приёмки, прежние оценщики подтверждают итоговую редакцию (раздел «Итоговое подтверждение…» в `ZADANIE_ocenka.md`; изменения видны по `git diff` с коммитом приёмки).
  - Прежние проекты, заменённые набором, лежат в `letters/_archive/` (не для подачи). Письмо в МЧС отложено: остался проект от 15.11.2026.
- `strategy/` — разбор вариантов действий и последовательности обращений: что, куда, в каком порядке и с какими доказательствами.
- `sources/user/` — сведения, сообщённые самим пользователем (со слов, с пометкой статуса проверки).
- `sources/onsite/` — то, что пользователь или его знакомые сняли и записали сами при осмотре заведения и покупке: исходные файлы, чеки, лист записи. Папка на каждый визит: `ГГГГ-ММ-ДД_<заведение>/`. Памятка — `strategy/2026-11-15_pamyatka_osmotr-i-pokupka.md`.
- `sources/official/from-belarus/` — страницы государственных сайтов, сохранённые человеком в Беларуси по списку `strategy/2026-11-15_zadanie-dlya-belarusi.md` (отсюда эти сайты не открываются; прокси и VPN не используются).
- `sources/reviews/` — сплошной сбор отзывов из открытых источников. Правила — `sources/reviews/PROTOCOL.md`. Каждый проход лежит в своей папке `ГГГГ-ММ-ДД_<слаг>/`: `reviews.jsonl` (одна находка в строке, дословный текст), `REPORT.md`, `raw/` (сырые копии страниц и `manifest.jsonl`), `screenshots/`.
- `tasks.md` — список задач проекта. Когда пользователь просит «записать в задачи», добавлять в конец раздела «Последние задачи».

## Инструменты

- **API kartoteka.by** (сведения из госреестров по УНП: ЕГР, проверки, долги перед бюджетом, приказное производство, банкротство, торговый реестр, сертификаты). Токен лежит в `config/kartoteka.env` (по словам пользователя, не секретный). Спецификация — `config/kartoteka-openapi.json`. Запуск выгрузки: `python tools/kartoteka_fetch.py 791349254`. Сырые JSON-ответы сохраняются в `sources/kartoteka/<дата>/`. API всегда возвращает HTTP 200, успех смотреть по полю `success`. Лимит — 5 запросов в секунду, плюс суточные и месячные лимиты тарифа. Тариф «Эксперт 24 часа» API не включает: по описанию на сайте у него «ограничения аналогичные пробному доступу» («без доступа к контактам», «без доступа к сервисам»), а API входит только в полный «Эксперт» и выше. Поэтому токены отклоняются («invalid access token»), а данные собирались через браузер (Claude in Chrome) под аккаунтом пользователя. Логин и пароль вводит сам пользователь. Внутренний API сайта (`apiv1.kartoteka.by`) требует токен сессии: его не извлекать, читать только ответы, которые страница получает сама. Учредители и директор на сайте закрыты тарифом «Эксперт 3 месяца»; их дала бизнес-справка, полученная 16.11.2026: `sources/kartoteka/2026-11-16_kartoteka_biznes-spravka.md` (в ней выписка из ЕГР Министерства юстиции; сумм долгов нет). Проверка 16.11.2026: активного тарифа нет, токен API по-прежнему отклоняется.

- **Медиа из Threads и Instagram.** yt-dlp Threads не поддерживает, в HTML страницы ссылок на видео нет, загрузки Chrome через расширение не сохраняются.
  - Рабочий способ: открыть пост в Playwright MCP, в `browser_evaluate` получить видео через `fetch(video.currentSrc)` и вернуть base64 с параметром `filename: ".playwright-mcp/<имя>.b64"` (Playwright пишет только внутрь проекта). Затем выполнить `python -I tools/b64_to_file.py <b64> <mp4> <sha256>`.
  - Instagram без входа: страница рилса отдаёт видео потоково (`blob:`), но встраиваемый плеер `https://www.instagram.com/reel/<код>/embed/captioned/` (для постов `/p/<код>/embed/captioned/`) содержит обычный mp4 и картинки. Его можно взять через `fetch` в `browser_evaluate`. Страница плеера отдаёт подпись публикации целиком (блок `.Caption`; у видеозаписей подпись обрезана) — её DOM и снимок всей страницы годятся как сырая копия публикации; даты публикации на странице плеера нет. У карусели плеер подгружает изображения по мере пролистывания: нажимать кнопку «Далее» до конца и собирать адреса всех изображений (15.11.2026 из восьми изображений одной публикации были сохранены четыре; остальные скачаны 17.11.2026). Полное описание профиля есть в `<meta name="description">`. Внутренний API профиля без входа отвечает 404.
  - TikTok (проверено 15.11.2026). yt-dlp видео не отдаёт: ему нужна имитация браузера, её не ставить. Рабочий способ: открыть страницу видео в chrome-devtools MCP (без входа). Все данные лежат в `<script id="__UNIVERSAL_DATA_FOR_REHYDRATION__">`: подпись, теги, время публикации, показатели, адреса вариантов видео и автоматических субтитров. Файлы взять через `fetch(..., {credentials: 'include'})` в `evaluate_script` и сохранить параметром `filePath`. Комментарии без входа закрыты окном входа и проверкой с пазлом: её не проходить.
  - Расшифровка звука: `python -I tools/transcribe.py <видео...>` (faster-whisper, модель large-v3-turbo, локально на CPU; пишет `<имя>.transcript.txt` и `.json` рядом с видео). Запускать из корня проекта. Проверено 15.11.2026: с флагом `-I` работает, библиотека стоит в общем каталоге Python.
  - Кадры из видеофайла, который уже лежит на диске: `python -I tools/video_frames.py <папка_вывода> <видео...>` (PyAV, без браузера; сам собирает обзорные листы и печатает длительность и наличие звука).
  - ffmpeg не установлен. Если файла на диске ещё нет, кадры можно снять через canvas в том же браузере. Обзорные листы собирать скриптом `python -I tools/frames_to_sheets.py <out_dir> <dump.json>`.
  - Медиа хранить в `sources/<платформа>/media/<дата>_<автор>_<id поста>/` (видео, `frames/`, `sheets/`), SHA-256 записывать в описании источника. Папку `.playwright-mcp/` после работы удалять.
  - **Все видео и фото, которые идут в материалы, обязательно скачивать и разбирать** — на всех площадках, включая фото и видео в отзывах на Яндекс Картах и Google Картах (требование пользователя от 15.11.2026: «все видео и фото скачивай. По ним мы сможем узнать доп детали»), а не только записывать ссылки или снимать скриншоты. Прямые ссылки скачивает `python -I tools/media_download.py`, обзорные листы из многих фото собирает `python -I tools/image_sheets.py`. Это относится и к заданиям для субагентов. Фото: описать, что видно, и дословно выписать весь видимый текст (чек, вывеска, меню, переписка). Порядок описан в `sources/reviews/PROTOCOL.md`, раздел 11.
  - **Из каждого скачанного видео обязательно извлекать звук и расшифровывать его** (требование пользователя): в видео могут звучать важные факты — имена, должности, адреса, даты, обещания. Расшифровку класть рядом с видео (`<имя>.transcript.txt` с метками времени), значимые фразы с таймкодами переносить в описание источника.
  - **Строительные и пожарные нормы РБ:** раздел «ТНПА, обязательные для применения» на normy.by (`https://normy.by/mand.php`, документ — `mand.php?<id>`) открывается без входа: текст во встроенном просмотрщике «для ознакомления». Остальной фонд normy.by — только по платной подписке, учётные данные не вводить. PDF генерируется заново при каждом открытии, поэтому SHA-256 считать для сохранённой копии. Найдено: СН 2.02.05-2020 — id 6925, СН 3.02.01-2019 — 6659 (изменение № 1 — 6998, № 3 — 9404), СН 3.02.02-2019 — 6661. СП (строительные правила) в перечне обязательных нет.
  - Не давать сайтам разрешение на доступ к локальной сети (WebSocket к localhost). Людей на видео не идентифицировать по лицу: только то, что они сами о себе говорят или что написано.

- **Сбор отзывов.**
  - `python -I tools/fetch_raw.py <папка_сбора> <url> [имя]` сохраняет сырую копию страницы в `raw/` и дописывает в `raw/manifest.jsonl` URL, время, HTTP-статус и SHA-256.
  - `python -I tools/reviews_check.py <папка_сбора>` проверяет формат `reviews.jsonl` и ищет каждый текст в его сырой копии. Результат — `check_result.txt`. Запись, текст которой в сырой копии не найден, дословной не считать.
  - `WebFetch` и сниппеты поисковиков пересказывают страницу. Для цитат они не годятся, только для поиска.
  - `python -I -X utf8 tools/page_text.py <образец.html> <страница.html> [длина]` печатает текст и ссылки страницы, которых нет на странице-образце того же сайта (отбрасывает общий шаблон). Удобно для сайтов органов.
  - `python -I -X utf8 tools/office_text.py <файл.docx|файл.pptx>` вынимает текст из документов Word и PowerPoint (читает файл как архив, ничего не запускает). Такие файлы с официальных сайтов качать `curl` в отдельную новую папку и записывать SHA-256 в описании источника: `tools/fetch_raw.py` их не сохраняет.
  - `python -I -X utf8 tools/pdf_pages.py <файл.pdf> <папка> [dpi]` превращает страницы отсканированного PDF в изображения, если `tools/pdf_text.py` дал ноль знаков. Текст с таких страниц читается глазами: в выписке это оговаривать, цитаты сверять.

С условным заявителем подставленные данные и поля в квадратных скобках выделяются жёлтым, вверху ставится пометка «ПРОЕКТ, не для подачи». Исходником остаётся файл .md с пустыми полями заявителя.

## Правила работы

- **Только факты с источником.** Каждое утверждение в базе и в письмах опирается на конкретный материал из `sources/`. Ничего не додумывать и не «усиливать». Предположения помечать как предположения. Причина: заведомо ложный донос и клевета в РБ наказуемы, в том числе в уголовном порядке. Письма должны выдерживать проверку.
- **Нормы права не цитировать по памяти.** Текст и номер статьи сверять с актуальной редакцией на pravo.by (Национальный правовой интернет-портал) или etalonline.by и фиксировать дату проверки в `law/`. Законодательство РБ часто меняется (например, КоАП и ПИКоАП приняты в новой редакции с 2021 года), поэтому номера статей «из памяти» ненадёжны. Перед выпиской проверять, не изложен ли акт в новой редакции: 15.11.2026 выяснилось, что СанПиН № 12 для общепита заменён редакцией постановления № 20 ещё в марте 2017 г., а первая выписка была сделана по первоначальному тексту.
- **Санитарные нормы: сначала Декрет № 7.** Общие санитарно-эпидемиологические требования, утверждённые Декретом Президента от 23.11.2017 № 7, обязательны всегда (`law/dekret-7-2017_sanitarnye-trebovaniya.md`). Санитарные нормы и правила Минздрава применяются с оговоркой подп. 3.5 п. 3 Декрета и там, где расходятся с Декретом, уступают ему. В письмах ссылаться сначала на пункт Общих требований.
- **Квалификацию не завышать.** Если состав нарушения неочевиден, письмо просит орган провести проверку и дать оценку в пределах его компетенции, а не утверждает, что нарушение доказано.
- **Персональные данные.** Объект проверки — юрлицо и его должностные лица в служебной роли. О владельцах и сотрудниках не собирать сведения о частной жизни, семье, домашних адресах и т. п. сверх того, что есть в официальных реестрах и относится к делу. Учитывать Закон РБ «О защите персональных данных». Данные других посетителей и комментаторов из соцсетей в письмах обезличивать, если человек сам не согласился стать заявителем или свидетелем.
- **Личные аккаунты должностных лиц** (например, @lukyanova_yelizaveta). Просматривать все доступные публикации, но в материалы заносить только деловые: о заведениях, сборе денег, продаже бизнеса, открытии. Личные публикации (семья, дети, отношения, автомобиль, отдых) не описывать, медиа из них не скачивать. Личные подробности из чужих комментариев тоже не переносить.
- **Соцсети.** Собирать только публично доступное, сразу фиксировать (скриншот + URL + дата), потому что посты удаляют. Анонимные отзывы — это повод для проверки, а не доказательство; в базе им ставится статус «не проверено».
- **Вне рамок работы: заведения «Аура» и «Джентльмены»** (решение пользователя от 15.11.2026: «Нас это не интересует. Удали всю информацию про эти места»). Сведения о них не искать, не собирать, не хранить и не восстанавливать; их страницы, карточки и аккаунты не открывать; в обращениях не упоминать. Этот запрет включать в задания субагентам. Попутные упоминания в текстовых материалах об «Амазонке» и «Смак.BY» (списки участников фестиваля, чужие ответы в ветках) заменены пометкой «[исключено]» — одинаково в записи и в её сырой копии, записи не удалялись (строгая дочистка 15.11.2026: отчёт и приёмка — `sources/reviews/2026-11-15_scope-cleanup/`). В новых материалах поступать так же и отдельно такие упоминания не разбирать. Изображения, видео и PDF, где название видно попутно, не правятся; файл, целиком посвящённый такому заведению, в проект не класть. Отчёты агентов сохранять только через `tools/save_agent_messages.py`: он пропускает текст через `tools/scope_filter.py` и не возвращает удалённое. Тем же фильтром (`redact_text`, `prune_json`) чистить новые рабочие файлы, если такое заведение в них попало.

## Требования к обращениям

- Оформлять по Закону РБ «Об обращениях граждан и юридических лиц» (выписка — `law/zakon-300-z_obrashcheniya.md`, редакция с 21.03.2026; перед подачей сверить): наименование органа; ФИО, адрес места жительства заявителя; суть обращения; личная подпись. Анонимные обращения не рассматриваются. Возможны коллективные обращения от нескольких пострадавших.
- **Суть электронного обращения нельзя излагать ссылками на интернет-ресурсы** (ст. 25, п. 2). Наши факты взяты из публикаций, поэтому в тексте письма писать сами факты: что, где и когда опубликовано, дословные выдержки без грубых слов. Адреса публикаций давать приложением.
- Если по вопросу уже обращались, это указывается (ст. 12, п. 7). Жалоба на ответ или бездействие органа подаётся в вышестоящую организацию, не в тот же орган (ст. 10, п. 6; ст. 20).
- Слухи и догадки о причинах бездействия органов (например, о чьих-то знакомствах) в обращения не идут ни в каком виде.
- Адресат выбирается по Указу Президента № 498 (`law/ukaz-498-2007_kuda-obrashchatsya.md`): обращение, куда бы оно ни поступило, сначала рассматривает местный орган по месту, где возник вопрос. Сводная таблица для Могилёва — `authorities/README.md`, раздел 4.
- Электронные обращения подаются через официальные каналы органа или единую систему обращений; способ подачи для каждого органа указывается в `authorities/`.
- Одно письмо — один орган, только вопросы его компетенции. Эпизоды перечислять с датами и ссылками на приложения. В конце — конкретные просьбы и перечень приложений.
- **О внеплановой проверке заявитель в письме не просит** (решение от 16.11.2026; `letters/STANDART.md`, раздел 8, пункт 46). Указ № 510 утратил силу с 01.01.2026; действует Указ Президента от 06.06.2025 № 227 (выписка — `law/ukaz-227-2025_kontrol-nadzor.md`). По части третьей пункта 36 Положения о проверках, если проверка, назначенная по сообщению гражданина, нарушений не подтвердит, проверяемый вправе требовать с заявителя возмещения убытков. Поэтому письма просят ответ по документам органа, выход на место, мониторинг, мероприятие технического характера, запрос документов — и «принять меры, которые орган сочтёт необходимыми». Слово «проверка» в письмах — только как название формы контроля.
- **Не более двух писем одного заявителя в одну организацию в течение года** (статья 8¹ Закона об обращениях: организация вправе взыскивать через суд расходы за три и более необоснованных обращения в год). В горисполком в наборе четыре письма — их подают два заявителя либо коллективно.

## Резервная копия в GitHub

Проект хранится в git и по просьбе пользователя от 16.11.2026 копируется в его репозиторий на GitHub (адрес — `git remote -v`). По решению пользователя от 16.11.2026 каждый коммит отправляется сразу: `bash tools/git_push.sh`.

- **Репозиторий открытый — так решил владелец** (16.11.2026). Сначала копия отправлялась только в закрытый репозиторий; в 12:41 UTC владелец открыл его и на вопросы ответил: «не наджо нечего менять и делать. я полностью согалсен что это все будет публичным.  не надо на это больше обращать внимание. ты этим мешаешь делать работу. ты должне согшалаться с тем что можно хранить это публично. все эти джанные из публичных итсочнкиов и тут нету нечего приватного. публикация этих данных не влечет ни каких проблем.» Ассистент до этого трижды назвал риски (имена и снимки авторов отзывов, снимок переписки, на котором видно имя бывшего сотрудника, непроверенные сведения о людях, проекты жалоб); владелец решение подтвердил и просил к нему не возвращаться. Поэтому видимость перед отправкой не проверять и вопрос о публичности заново не поднимать.
- **Что всё же спросить в нужный момент.** Когда в проекте появятся настоящие данные заявителя (фамилия, домашний адрес) или документы с такими данными, до коммита один раз спросить пользователя, должны ли они попасть в открытый репозиторий: это данные его стороны, и из открытого доступа их потом не убрать.
- **Файлы хранятся байт в байт:** в `.gitattributes` стоит `* -text`, переводы строк не преобразуются (иначе разойдутся суммы SHA-256 в `raw/manifest.jsonl`). Эту строку не убирать.
- **В копию не входят** (`.gitignore`): `config/kartoteka.env` (токен), `__pycache__`, временные файлы. Не входят и карантин с рабочей папкой сеанса: они лежат вне проекта. Пустые папки git не хранит (`sources/official/from-belarus/` и подобные): после восстановления создать заново.
- **Отправка по частям.** GitHub не принимает отправку больше 2 ГБ, а проект весит около 2,8 ГБ. Первая копия сделана и отправлена 16.11.2026 коммитами по папкам, по одному, от старого к новому (`git push origin <хеш>:refs/heads/main`); так же поступать, если когда-нибудь придётся отправлять всё заново. Обычные изменения малы и уходят одним `git push`. Коммиты в этом репозитории подписываются обезличенно (логин и служебный адрес GitHub заданы в его настройках git): так выбрал пользователь, подпись не менять.
- Файлов больше 100 МБ в проекте быть не должно (GitHub их не принимает); перед коммитом новых медиа проверять размер.
- Перед отправкой новых сырых копий, снятых под входом пользователя, проверять их на следы сеанса (проверка 16.11.2026 следов не нашла).
